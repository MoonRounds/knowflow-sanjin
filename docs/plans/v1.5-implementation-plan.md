# KnowFlow V1.5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: 执行阶段用 superpowers:executing-plans 或 superpowers:subagent-driven-development 逐任务实施。本计划为 Phase 级粒度；进入某 Phase 前，将其 In Scope 细化为任务级 PLAN 并遵循 `docs/plans/WORKFLOW.md` 的「执行 → 独立 Review → 修复 → Owner 验收」生命周期。

**Goal:** 将知识库整理为 `KnowledgeBase → Document → Chunk` 三层统一结构（单归属），并把 RAG 从「纯自动 Router」扩展为「用户可手动绑定 0..N 知识库」的问答能力。

**Architecture:** 以已接受的 ADR 0007（单归属）为地基，把 `knowledge_item` 全链路改名为 `knowledge_document`；页面从「一页多职责」拆为「库列表 → 库详情文档列表 → 文档详情」三层；`conversation` 增加可选知识库绑定，非空时 Router 收敛到集合内、为空走现有自动 Router。

**Tech Stack:** Java 21 / Spring Boot 4.1 / MyBatis-Plus + MySQL 8.4 + Flyway；Vue 3 + TS + Element Plus；Qdrant、Redis、RabbitMQ（均沿用现有基线，不引入新框架）。

---

## 0. 背景与已确认决策（grilling 产出）

V1 现状：`knowledge_base` ↔（多对多 `knowledge_base_item`）↔ `knowledge_item` → `knowledge_chunk`；三种来源（`AI_CONVERSATION` / `MANUAL_NOTE` / `UPLOAD_FILE`）统一为 `knowledge_item`；RAG 纯自动 Router，Conversation 与知识库零关联；`KnowledgeBasesView` 一页混排库列表 + 我的笔记 + 上传。存量极小（1 KB / 10 Item / 70 chunk / 29 会话），Qdrant 当前 0 点，需全量重建。

已确认决策：

| 编号 | 决策 |
|---|---|
| Q1 | `Document` = `KnowledgeItem` 统一定名，不新增层级；三层即 KB → Document → Chunk |
| Q2 | 问答助手 = 现有 Chat 页增强，不建独立页面 |
| Q3 | 手动选库存 Conversation（0..N，可为空）；非空时 Router 收敛到集合，为空走自动 Router |
| Q4 | 存量几十条、Qdrant 空 → 低成本回填 + 全量重建 |
| Q5 | 物理全改：表/类/API/前端类型 `knowledge_item → knowledge_document`，与 ADR 0007 合并为一次迁移 |
| Q6 | 新建会话可多选库；会话内顶部面板可增删；0 库 = 自动 Router |
| Q7 | 页面拆三层：库列表 → 库详情（文档列表）→ 文档详情；笔记并入 `source_type` 过滤，无独立入口 |
| Q8 | Document 级 `index_status`；上传文件「解析 + 索引」两段状态；前端聚合展示，不做 Chunk 级状态 |
| Q9 | 引用基础增强：来源面板补 KB 名与来源类型；正文 `[S1]` 可点击悬停预览 |
| Q10 | 检索保持全局 Top-K + OR filter；每库均衡配额留 V2.0 |
| Q11 | V1.5 范围见各 Phase In Scope；V2.0 留语义搜索/混合检索/段落级引用/均衡检索/版本对比/Tag 参与 RAG |

## 1. Phase 总览

| Phase | 主题 | 数据库迁移 | 结束态可运行性 |
|---|---|---|---|
| 1 | 数据模型与领域改名（ADR 0007 落地） | V12 | 前后端编译/测试绿，页面布局不变，自动 RAG 回归正常 |
| 2 | 页面结构拆分（三层页面） | 无 | 三页面闭环，旧链接重定向 |
| 3 | 手动选库问答（Conversation 绑定 + Router 收敛） | V13 | 手动/自动两种模式均可问答，旧行为不变 |
| 4 | 状态聚合 + 引用增强 + 文档/验收 | 无 | V1.5 三闭环通过，verify-all 绿 |

每个 Phase 遵循 WORKFLOW.md：执行 → 本地验证 → commit → 独立 Review → 修复 → 复审 → Owner 验收 → 下一 Phase。

## Phase 1：数据模型与领域改名（V12）

**目标：** 把 `knowledge_item` 体系重构为 `knowledge_document` 单归属体系，后端全链路改名 + API/前端契约改名，落地 ADR 0007（`kb_id` 必填、删关联表、软删统一 `deleted`），不改任何页面布局与交互。

**In Scope：**
- V12 迁移：`knowledge_item → knowledge_document`（RENAME）；加 `kb_id`（回填后 NOT NULL + FK + 索引）；加 `deleted` 并从 `status` 回填后删 `status`；`knowledge_chunk → knowledge_document_chunk`；`knowledge_item_tag → knowledge_document_tag`；DROP `knowledge_base_item`；`tag` 加 `deleted` 并调整唯一约束；`knowledge_candidate.ai/draft_knowledge_base_ids`（CSV）→ 单值 `ai/draft_knowledge_base_id`
- 后端改名：`modules.knowledge` 内 `KnowledgeItem → KnowledgeDocument`、`KnowledgeChunk → KnowledgeDocumentChunk`、`KnowledgeBaseItem` 删除，mapper/assembler/dto/vo/service/controller 同步
- 模块重命名：`modules.document`（上传文件）→ `modules.file`，消除与 Document 概念的命名冲突
- API 改名：`/knowledge-items` → `/documents`；上传、建笔记、候选确认的 `knowledgeBaseIds` 数组 → 单值 `knowledgeBaseId`（必填）
- Qdrant payload：`knowledge_base_ids` 数组 → `knowledge_base_id` 单值；`RetrievalService` 二次校验从读关联表改为读 `kb_id` + KB 状态
- 前端契约同步：`api/knowledge-items.ts → api/documents.ts`、`types/knowledge-item.ts → types/document.ts`、重新生成 `generated.ts`；`KnowledgeItemDetailView` 路由、`ChatView`/`MessageSourcesPanel` 跳转、`KnowledgeBasesView` 调用改引用；`CandidatesView` 的库选择器从多选改单选（不重构布局）
- 存量回填 + Qdrant 全量重建（对 ACTIVE 且缺索引/索引过期的 Document 触发 reindex）

**Out of Scope：** 页面布局重构（P2）、`conversation.knowledge_base_ids`（P3）、引用增强与状态聚合（P4）、每库均衡检索（V2.0）。

**数据库迁移：** 单次 `V12__knowledge_document_restructure.sql`。表 RENAME 时 MySQL 自动跟随外键，`file_metadata`/`knowledge_candidate`/`processing_task` 不受影响。迁移需在「干净库」与「存量库」各验证一次。

**关键文件：**
- 新建：`docs/adr/0009-…`（见 P4，本阶段可不建）——不，ADR 0009 放 P4；本阶段仅 migration
- 迁移：`knowflow-app/src/main/resources/db/migration/V12__knowledge_document_restructure.sql`
- 后端：`modules/knowledge/**`（entity/mapper/assembler/dto/vo/service/controller/infrastructure）、`modules/rag/service/RetrievalService.java`、`modules/rag/dto/*`、`modules/document/**` → `modules/file/**`
- 前端：`api/knowledge-items.ts`、`api/types/knowledge-item.ts`、`api/types/generated.ts`、`views/KnowledgeItemDetailView.vue`、`views/CandidatesView.vue`、`views/KnowledgeBasesView.vue`、`views/ChatView.vue`、`components/MessageSourcesPanel.vue`

**任务：**
1. 编写 V12 migration（改名、加列、回填、删列、DROP 关联表、candidate 单值），在干净库验证，在存量库验证回填正确（10 Item 全部得到 `kb_id`，`status=DELETED` 映射到 `deleted=1`）
2. 后端实体/映射/服务/控制器全链路改名并重编译，`modules/document → modules/file` 包迁移
3. `RetrievalService` 二次校验改 `kb_id`；Qdrant payload 构建与 filter 改单值
4. API 改 `/documents` + 单值 `knowledgeBaseId`；DTO/Assembler 同步
5. 前端 API 模块、类型、`generated.ts` 重新生成；引用与跳转改名；`CandidatesView` 库选择改单选
6. 存量回填 + Qdrant 全量重建；上传→索引→自动 RAG 检索引用、提取→候选→确认→沉淀→检索回归
7. 跑 `scripts/verify-fast.sh` 与 `scripts/verify-integration.sh`

**结束状态（可运行）：** 前后端均编译通过、测试绿；UI 布局与交互不变；新建笔记/上传/提取候选确认均归入唯一 KB；自动 Router RAG 正常；检索命中后二次校验走 `kb_id`。

**验收标准：**
- V12 在干净库与存量库均通过；10 Item 回填 `kb_id` 正确；软删状态映射正确
- 后端编译、单测、集成测试绿；前端 typecheck/build 绿
- `/documents` 契约正确，无 `/knowledge-items` 残留引用
- 上传→索引→检索→引用、提取→候选→确认→沉淀→检索两条闭环回归通过（手动模式未接线）
- Qdrant 重建后检索命中，二次校验走 `kb_id` 单值
- 页面 UI 布局未改变

**兼容性：** UI 布局与交互不变；API 路径变化为 Q5 刻意的契约变更，前后端在同一 Phase 内同步完成，无中间不兼容窗口。

## Phase 2：页面结构拆分

**目标：** 把一页多职责的 `KnowledgeBasesView` 拆为「库列表 → 库详情（文档列表）→ 文档详情」三层页面；「我的笔记」并入 `source_type` 过滤视图；补齐 Tag 过滤。

**In Scope：**
- 路由：`/knowledge-bases`（库列表）、`/knowledge-bases/:id`（库详情 = 该库文档列表，含新建笔记/上传入口、`source_type`/Tag/索引状态过滤）、`/documents/:id`（文档详情）
- 前端：`KnowledgeBasesView` 拆为库列表页 + 新增 `KnowledgeBaseDetailView`；`KnowledgeItemDetailView → KnowledgeDocumentDetailView`；新建笔记/上传对话框迁入库详情页；Tag 过滤 UI

- 旧路由 `/knowledge-items/:id` → redirect `/documents/:id`
- 导航菜单更新（无独立「我的笔记」入口）
- 回归：聊天、候选、处理页不受影响

**Out of Scope：** 手动选库（P3）、引用增强与状态聚合展示增强（P4）、语义搜索（V2.0）。

**数据库迁移：** 无。

**关键文件：**

## Phase 3：手动选库问答

**目标：** `conversation` 支持绑定 0..N 知识库；手动模式 Router 收敛到集合内；前端提供会话选库 UI；0 库时行为与 V1 完全一致。

**In Scope：**
- V13 迁移：`conversation` 加 `knowledge_base_ids JSON NULL`（`NULL`/`[]` = 自动 Router）
- 后端：`Conversation` 实体/API —— `CreateConversationRequest`/`UpdateConversationRequest` 加可选 `knowledgeBaseIds`，校验库存在且 `enabled`（禁用库不可选）
- `RouterService`：入参含会话绑定集合；非空时候选集合收敛为该集合（仍保留「是否需要 RAG」判断），`router_json`/`retrieval_json` 记录 `mode: MANUAL|AUTO`
- 手动模式语义：选定库但问题无关时 Router 判 `NOT_NEEDED` → 普通回答，`chat_message.rag_status` 语义不变，前端提示「当前已绑定 N 个库」
- 前端：会话创建引导可多选库；会话内顶部面板展示并随时增删库；发送消息时使用会话绑定
- OpenAPI/前端类型同步
- 回归：未绑定库的新旧会话走自动 Router，行为与 V1 一致

**Out of Scope：** 每库均衡检索（V2.0）、引用增强与状态聚合（P4）、语义搜索（V2.0）。

**数据库迁移：** `V13__conversation_knowledge_base.sql`，仅加一列 JSON，兼容 NULL（历史会话即自动模式）。

**关键文件：**
- 迁移：`V13__conversation_knowledge_base.sql`
- 后端：`modules/conversation/entity/Conversation.java`、`dto/CreateConversationRequest.java`、`dto/UpdateConversationRequest.java`、`service/ConversationService.java`、`controller/ConversationController.java`；`modules/rag/service/RouterService.java`、`RagContextBuilder.java`、`dto/*`
- 前端：`views/ChatView.vue`（选库面板）、新建会话引导组件、`api/conversations.ts`、`api/types/generated.ts`

**任务：**
1. V13 迁移加列，后端 Conversation 实体/API 增加 `knowledgeBaseIds` 与校验
2. `RouterService` 支持「候选集合收敛」；trace 记录 `mode`；手动模式 `NOT_NEEDED` 语义
3. 前端会话选库 UI（创建引导 + 会话内可改）；发送消息带会话绑定
4. OpenAPI 重新生成前端类型
5. 回归：0 库自动 Router 行为与 V1 一致；提取/候选流程不受影响
6. 跑 `verify-fast.sh` / `verify-integration.sh`

**结束状态（可运行）：** 用户可在会话内手动绑定 0..N 库并即时生效；手动问答引用正确；未绑定时自动 Router 行为与 V1 完全一致。

**验收标准：**
- 手动选 1 库/多库问答，引用来源命中选定库且展示正确
- 手动选库但问题无关 → 普通回答，`rag_status` 提示正确，前端显示绑定状态
- 0 库 = 自动 Router，行为与 V1 回归一致
- 会话内增删库即时生效（下一轮生效）
- 提取（Conversation Extraction）/候选审核流程不受影响
- 前后端编译、单测、集成测试绿

**兼容性：** `knowledgeBaseIds` 可选，历史会话与未绑定会话完全沿用自动模式；`rag_status` 枚举与 SSE 事件协议不变。

## 2. 风险与前置条件

1. **未提交工作区改动**：当前 `RetrievalService`/`QdrantClient`/`KnowledgeIndexingService`/`ModelSettingsView` 等含未提交的 embedding 改动。P1 开工前先确认现状（提交或暂存），避免混入 P1 diff。
2. **Qdrant 空疑似 Embedding 配置未成功**：全量重建前必须先确认 Embedding 配置可用并测通（`embedding_config` 已建表，见 ADR 0008）。
3. **candidate 多选→单选回填**：历史候选若存在「一候选多库」，主归属取第一个会丢语义；当前 10 条候选需核对。
4. **手动选库 ≠ 强制命中**：选定库但问题无关时 Router 判 `NOT_NEEDED` → 普通回答，产品语义须在 UI 明确提示。
5. **`knowledge_base_ids` 用 JSON 列**：牺牲「某库被哪些会话使用」的查询能力，V1.5 无此需求，可接受；如需强关联查询，改为关联表（升级到 V14 前与 Owner 确认）。
6. **表 RENAME + Flyway history**：旧迁移（V1–V11）引用的旧表名不可回改；RENAME 只作用于 V12 及之后，P1 集成测试须覆盖存量库路径。
7. **OpenAPI 类型再生成**：P1/P3 后端改名后须重新生成前端 `generated.ts`，契约同步是每个 Phase 的硬验收项。

## 3. 决策变更登记

- P3 的「手动知识库选择」变更 DECISIONS §13「V1 不提供手动知识库覆盖」——进入 P3 前以 ADR 0009（或独立 ADR）先行确认。
- P1 落地 DECISIONS §10 与 ADR 0007 的「单归属 + 删关联表 + 软删统一」，实现代码与已确认决策对齐。
