ConcurrentHashMap 为什么线程安全？

知
本轮未调用个人知识库 · 使用当前会话上下文

关键不是“用了锁”，而是锁的粒度和并发控制方式。

以 JDK 8 为例，ConcurrentHashMap 取消了 Segment，核心结构变成数组 + 链表 / 红黑树。写入时会结合 CAS 与 synchronized，把竞争尽量限制在单个桶节点上，而读取大多不需要加锁。

JDK 8：CAS 初始化 / 定位桶 → 桶为空直接 CAS → 冲突时锁住桶头节点 → 链表或红黑树更新

所以它的“线程安全”不是来自一个全局大锁，而是来自一组针对不同状态设计的并发控制策略。

那 JDK 7 呢？为什么后来要改？

知
已理解“那”仍指 ConcurrentHashMap · 会话记忆命中

JDK 7 的核心是 Segment 分段锁。可以把整个 Map 想成被拆成多个独立小区域，每个 Segment 自己持有一把 ReentrantLock。

它比 Hashtable 的全表锁并发度高很多，但 Segment 本身是一层额外结构，而且并发粒度最终受 Segment 数量影响。JDK 8 把锁进一步下沉到桶节点，结构也更直接。

JDK 7 的核心不是“锁少了”，而是把一张表拆成多个可独立加锁的 Segment。

你上一轮问的是 ConcurrentHashMap，所以这里的“那”仍然沿用当前主题。JDK 7 通过 Segment + ReentrantLock 把不同 key 的写入竞争分散到多个区域。

JDK 7分段锁锁住 Segment
→
JDK 8桶级并发CAS + synchronized

后来改掉 Segment，主要是为了让结构更直接、并发粒度更细，同时避免固定 Segment 数量对并发度形成上限。
